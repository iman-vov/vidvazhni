# Редактор мап

Окрема сторінка для розробки (Ф2 у роадмапі): 2D-мапа зверху, плоскі гекси в осьових координатах `q,r` з тим самим розкладом, що й `src/render/hexLayout.ts`. Редагує `data/scenarios/<id>.json` у форматі `ScenarioDef` (`src/rules/content.ts`).

## Запуск

```bash
npm run dev
```

Відкрити `http://localhost:5173/vidvazhni/tools/map-editor/` (порт може бути інший, якщо 5173 зайнятий). Одразу відкрити сценарій: `…/tools/map-editor/?s=s3`.

Сторінка лежить у `tools/map-editor/` і є звичайною HTML-сторінкою під коренем Vite: дев-сервер її віддає, а `vite build` збирає лише `index.html` гри, тож редактор не потрапляє ні в `dist/`, ні в кеш PWA. Конфіг Vite не змінювався.

Типи редактора перевіряє `npx tsc -p tools/map-editor --noEmit` (кореневий `tsconfig.json` не включає `tools/`; модулі `model.ts`, `checks.ts` проходять і через `npx tsc --noEmit`, бо їх імпортують тести).

## Що вміє

| Інструмент (клавіша) | Що робить |
|---|---|
| Гекси (`h`) | малювати гекси активної кімнати мишею; права кнопка стирає. Гекс іншої кімнати переходить разом з усім, що на ньому |
| Стерти гекс (`e`) | гекс разом зі стінами, спавнами, стартом, метою на ньому |
| Місцевість (`t`) | небезпечна (терен), важка, вода; «звичайна» стирає |
| Стіна (`w`) | клік біля ребра ставить або знімає тонку стіну до сусіда |
| Перешкода (`o`) | з моделлю (`tree`, `rock`, `barrel`, `pillar`…) |
| Пастка (`p`) | шкода (порожньо = 2 + рівень) і стани |
| Двері (`d`) | куди ведуть (за замовчуванням сусідня кімната) і ключ |
| Монстр (`m`) | тип (монстри й боси) і ранг окремо для 2/3/4 героїв |
| Старт (`s`) | до 4 гексів у стартовій кімнаті, номер = порядок героїв |
| Монета (`c`), Скриня (`x`) | скриня з монетами, предметом крамниці або сюжетним предметом |
| Об'єкт (`j`) | важіль, жаровня, руна, жорна або будь-який інший вид; `state`, `blocks` |
| Вихід/доставка (`g`) | гекси мети `reachExit` або `carryItem` |
| Лінія зору (`l`) | два кліки: зелена лінія — видно, червона — ні |
| Що тут? (`i`) | усе на гексі з кнопками видалення; фігура чи перешкода стає налаштуванням інструмента |

Праворуч: поля сценарію (мета, бос або предмет, стартова кімната, нові правила, specials, нагорода, сфери форку на старті й щораунду), кімнати як шари з кольором (видимість, перейменування з оновленням дверей, видалення, нова кімната), здобич з монстрів активної кімнати (`drops`), живі перевірки, таблиця монстрів «зв.+ел. для 2 / 3 / 4» у нотації документа і сирий JSON, який можна правити й застосувати.

- **Undo/redo:** `Ctrl+Z`, `Ctrl+Y` / `Ctrl+Shift+Z`; мазок мишею — один крок.
- **Авто-стіни** (увімкнено): після кожної зміни межі між кімнатами закриваються стінами, крім гексів дверей. Це умова перехресних перевірок: кімнати з'єднані лише дверима. Кнопка «Закрити межі стінами» робить те саме разово.
- **Файли:** список `data/scenarios/*.json` (коли сторінку віддає дев-сервер), «Відкрити файл…», «Зберегти…» (`Ctrl+S`, у Chrome і Edge пише прямо у вибраний файл через File System Access API, інакше завантажує), «Завантажити JSON». Незбережена мапа переживає перезавантаження сторінки (`localStorage`).
- **Формат збереження** — як у `s1.json`: короткі об'єкти й списки гексів в один рядок, по 8 гексів, гекси кімнат відсортовані. Відкрити й зберегти файл без змін = той самий файл байт-у-байт (це перевіряє тест).

## Перевірки

`tools/map-editor/checks.ts`, ті самі в редакторі й у тестах:

1. JSON-схема `data/schema/scenarios.schema.json` (Ajv).
2. Спільні перехресні перевірки `tests/data/crossref.ts` (`checkScenario`): двері ведуть в існуючу кімнату й торкаються її, усе лежить у своїй кімнаті, на гексі не більше одного предмета, кімнати закриті одна від одної, старт у стартовій кімнаті, кожна кімната досяжна дверима, бос мети існує.
3. Перевірки мапи (`mapIssues`): ключ дверей дає скриня або здобич з монстра; монстр здобичі є в кімнаті; бос мети справді з'являється; предмет `carryItem` можна знайти; гекси мети не заблоковані; джерело `forkOrbs.eachRound` — id об'єкта; спавни, скрині, двері, монети й мета досяжні пішки від старту (двері відчинені, перешкоди й об'єкти з `blocks` непрохідні, тонкі стіни блокують); біля непрохідного об'єкта є вільний гекс.

Лінія зору рахується функцією рушія `lineOfSight` з `src/rules/los.ts` (без стану гри: будується лише `BoardState` з усіма кімнатами відкритими). Тож це те саме правило: видно, якщо хоч одна пряма між кутами гексів не торкається стіни. Через гекс дверей видно, бо між ним і сусідньою кімнатою немає стіни.

## Знімки мап

```bash
node tools/map-editor/snapshot.mjs
```

Малює кожен `data/scenarios/*.json` тим самим SVG-рендером, що й редактор (`render.ts`, завантажений через Vite), з легендою й таблицею монстрів, і пише PNG у `docs/screenshots/maps/<id>.png` (через `sharp`). Можна передати id: `node tools/map-editor/snapshot.mjs s2 s3`.

Позначки на мапі: синій кружок — старт героя; коричневий овал «→Б» — двері в кімнату Б, жовта «к» — з ключем; товста темна лінія — стіна; фіолетовий з шипами — терен (небезпечна), коричневий з рисками — важка, синій з хвилями — вода; червоний квадрат — пастка («L» = 2 + рівень); жовта монета; скриня (жовта крапка = сюжетний предмет); зелена пунктирна рамка — вихід або гекс доставки; кружок монстра з трьома квадратиками під ним — ранг для 2/3/4 героїв (порожній — немає, білий — звичайний, жовтий — елітний); великий кружок з червоним обідком — бос.

## Розширення формату (додавання, усе необов'язкове)

- `ScenarioDef.draft?: boolean` — мапа намальована в редакторі, ще не перевірена грою й балансом.
- `RoomDef.objects[].state?: string` — початковий стан (`up` у важеля, `unlit` у жаровні); у рушія вже є `Tile.object.state`.
- `RoomDef.objects[].blocks?: boolean` — об'єкт непрохідний, як перешкода (важіль, жаровня, жорна); руна прохідна.
- `RoomDef.drops?: { monster, questItem }[]` — сюжетний предмет, що падає з останньої фігури цього типу в кімнаті (ключ від ярусу в сценарії 4).
